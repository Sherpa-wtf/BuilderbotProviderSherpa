## Added optional consumer capabilities

- `provider.lifecycle` events: `{ state, socketGeneration, observedAt, reasonCode?, phoneNumber? }`; states connecting, ready, requires_link, disconnected, error. `socketGeneration` is local socket incarnation, **not** the Backend-authorized runtime generation. Only a real ready observation derives phoneNumber from the local linked socket identity; pulses never query it. Legacy ready/host/require_action/auth_failure remain for existing consumers.
- `getLifecycleSnapshot()` is a current observation, not desired intent or permission to resume.
- `setLifecycleGuard(async () => void)` runs immediately before socket `sendMessage`; rejection prevents a provider request. A second synchronous socket-generation check after the await protects a pause during authority validation. Bot consumers must bind the original work authorization, not substitute a fresh token after resume.
- `setLifecycleSendWrapper(descriptor, network)` encloses the actual socket request, after the guard. The network callback checks socket generation again after the durable claim await. No wrapper may mint authority.
- `setLifecycleIncomingGate(async (payload, dispatch) => boolean)` is optional for legacy consumers and mandatory for enrolled Bot. The gate awaits Backend admission, then calls `dispatch` synchronously under its private captured authorization; that callback rechecks local stop, deduplicates and emits without another await. Deferred work must be retained before return; errors reject before dedup. Healthy incoming does not become a new durable inbox, and EventEmitter handoff is not a downstream processing ACK.
- `recoverLifecycle()` invalidates the old socket and schedules ordinary transport reconnect without intentional-stop latch, logout or session deletion; used when ingress persistence fails or a stale event requires a new real observation.
- `stopLifecycle()` is one-way for that provider instance: clears its reconnect timer, fences old socket callbacks/sends, invalidates QR and calls `socket.end` without logout or deleting stored session. It does **not** prove ECS/PM2 has physically stopped. Only the control plane can confirm runtime shutdown.

## QR HTTP response change

The root endpoint no longer streams a filename from a prior process. It returns only a complete in-memory current challenge: PNG 200 with `Cache-Control: private, no-store`, `X-QR-Instance-Id`, `X-QR-Generation`, `X-QR-Revision` and `X-QR-Expires-At`. Missing, expired, disconnected or ready-invalidated challenges return 503 JSON `{ "state": "waiting_qr" }` with no-store. Callers expecting old 404 HTML refresh must handle 503 as pending and retry only while the linking view is active. Merely viewing QR never connects/resumes a runtime.

GET `/qr/metadata` returns `{instanceId, available, generation?, revision?, expiresAt?}` without raw QR. `instanceId` is a fresh boot UUID. Image queries `qrInstanceId`, `qrGeneration`, `qrRevision` are an all-or-nothing tuple: incomplete or stale tuples return 409 `qr_changed`, never the latest image.

Default generator validity is 40 seconds (matching socket qrTimeout); a newer challenge, socket replacement, ready or close invalidates it sooner. Atomic publication prevents partial-image and late-render overwrite races. This deadline is **not** a guarantee that WhatsApp will accept a scan until that time. The root remains behind the consumer's existing authenticated routing; this provider change alone does not add service authorization. Raw QR is never included in structured lifecycle events, but legacy require_action retains its existing payload for compatibility and must not be logged by consumers.
